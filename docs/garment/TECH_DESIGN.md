### 1.3 分阶段落实

当前原型仍是单SKU、9:16、固定模板、无动作参考：1张打样、10固定首轮、各1次改字及蒙版编辑，图像请求最多12次、`n=1`串行。原型优先沿用现有工作台，仅补验证所需的十位置映射及分层操作；十位置视图是业务能力，不要求另造整套工作台。进入完整产品化须满足8.1节的原型放行条件，再完成模板生产MVP、身份存储及20人验证，最后通过生产灰度与灾备验收。FR04为P1，静物F01、额外模型F02、自由图文画布F03后置；现有节点画布不替代F03。

## 2 架构与模块边界

### 2.1 目标结构

```text
浏览器
  → HTTPS入口 / 身份与发布路由
  → 稳定版或候选版 React + FastAPI
      → 应用服务 → PostgreSQL（业务、账号、发布、账本、Outbox）
      → 文件服务 → 私有MinIO
      → Outbox投递器 → Redis版本队列 → 对应ReleaseID的worker
          → GPT6 / GPT image（统一实际请求配额）
          → Pillow本地合成 → MinIO → PostgreSQL结果登记

独立恢复扫描器：截止时间、未知调用、取消收尾、Outbox补投递
生命周期服务：过期入回收站、引用检查、幂等物理清理
发布控制服务：测试证据、用户灰度、就绪检测、激活/回滚审计
异机备份服务：数据库备份 + MinIO对象清单及对象 + 恢复演练
```

测试环境另设完整资源与凭据，不接入生产队列。生产灰度的两个程序版本共享同一生产业务数据库和对象集合，因此必须同时兼容其结构；不能为候选版复制一份生产业务库再试图合并。

## 3 数据模型与不变量

### 3.1 通用约定

主键使用稳定标识。时间保存UTC，展示用用户时区；30天和7天按连续24小时计算，灰度工作日按部署时配置并展示的工作日历计算。不可变业务版本追加保存，反馈和选择的变化以事件记录；并发修改使用`row_version`。金额区分实际、估算及待核对，未知不记零。对象内容校验保存SHA-256，不把S3 ETag一概等同文件内容摘要。

Product、ProductionTask、ImageSession分别保存根归档标记，建议使用`archived_at`、`archived_by_user_id`及审计事件。归档独立于任务九状态、图片live/trashed/purged和软件Archive，不新增“已归档”任务主状态，也不靠删业务行或删文件表达归档。取消归档保留此前归档事件，不清除业务历史。

### 3.2 核心实体

| 领域 | 实体 | 关键字段/职责 |
| --- | --- | --- |
| 身份 | User、Team、TeamMembership、Session | UserID、用户名、密码哈希、角色、单个当前有效团队、启停、会话撤销版本；管理为部署级角色 |
| 商品依据 | Product、ProductEvidenceVersion | 团队共享编辑的商品及自由画布、SKU、证据原图、展示主图、事实版本、归档时间/操作者；关联正式任务独立授权 |
| 独立会话 | ImageSession | 独立TeamID、个人/团队范围、不可变创建者、当前负责人；范围及交接沿用任务权限，不依赖商品绑定 |
| 生产 | ProductionTask、ProductionBatch、ProductionItem | 不可变创建者、当前负责人、TeamID、共享范围、九状态、来源任务；正式任务与批次一对一，单SKU单规格十位置 |
| 计划配置 | PlanSnapshot、SlotPlan、OutputSpecVersion、ModelConfigVersion | 内容语言、文案预览版本及确认人/时间、确认提示词、事实、参考、模板、尺寸、模型真实ID/SDK/参数及凭据引用 |
| 执行 | ProductionOperation、ProductionAttempt、StageExecution | 轮次/父操作关联、接受时间与权限依据、类型、幂等键、父尝试、ReleaseID、输入摘要、派发顺序、有限截止、恢复记录及结果；执行所属轮决定版本，恢复溯源保留原尝试 |
| 模型与费用 | ModelCall、CostRecord | 调用类型、作用域、实际派发、provider请求ID、usage、费用核对状态 |
| 图文版本 | BaseImageVersion、MaskAsset、TextLayerVersion、LayoutVersion、CompositeVersion | 分层不可变内容、父版本、输入关系、实际尺寸、字体及渲染清单 |
| 图片与反馈 | ImageAssetVersion、FeedbackEvent、ItemSelection | 统一图片版本入口、源版本/复用时间、独立反馈与留存；正式位置当前采用版只引用合成成品 |
| 问题与处置 | OpenIssue、ItemDisposition | 未决失败/未知/本地恢复、当前候选与历史迟到输出的纳入记录；候选弃用与整个位置放弃分开 |
| 首轮 | FirstRoundAssessment、FirstRoundAssessmentItem | 固定原十位置及首次尝试/合成成品、新生或复用底图来源、反馈/质量快照、完整性及结算版本 |
| 素材 | ReferenceAssetVersion、TemplateVersion、StyleVersion | 内容、来源、标签、共享库版本及停用记录 |
| 对象 | AssetFile、AssetReference、AssetLease | bucket/key、大小摘要、对象状态；引用类别、有效期、使用租约及清理代数 |
| 下载与留存 | DownloadEvent、AssetLifecycleEvent | 完整传输证据、下载者；到期、删除、恢复、清理和原因 |
| 可靠性 | OutboxEvent、AuditEvent | 待投递事件、状态、幂等标识；操作者、事件顺序、前后版本 |
| 原型 | ExperimentRun | 配置及内部样例、图像额度12、计数、R_trial及证据包 |
| 发布 | ReleaseVersion、EnvironmentDeployment、CanaryAssignment、ReleaseEvent | 发布状态、不可变构建、兼容范围、路由代数、用户分组、旧版退出准入关闭时间/代数、测试/灰度证据及操作者 |

### 3.3 图片版本及生命周期字段

`ImageAssetVersion`至少包含：`id, team_id, resource_id, asset_kind, source_operation_id, parent_version_id, source_asset_version_id, file_id, generated_at, reused_at, restored_at, retention_started_at, first_downloaded_at, feedback, lifecycle, deleted_at, trash_reason, purge_after, legacy_protected, row_version`。字段名为建议；源版本、原生成时间与本次复用成功时间必须可区分。

- `asset_kind`区分底图、蒙版、合成图及自由节点输出；首次登记成功且对象可读时记录生成成功时间，不能从排队时间起算。
- `feedback`取`undecided/adopted/discarded`，显示为待定/采用/弃用；`lifecycle`取`live/trashed/purged`，与发布Active/Archive无关。
- 新生成图片的`retention_started_at`初值为`generated_at`；跨根资源复用生成图的新记录以`reused_at`为起点，保留原生成时间与源版本，`first_downloaded_at`不继承；未下载恢复时更新为恢复时间。收藏不创建新版本，不改变这些字段。
- `legacy_protected`是独立保护标记，不是假下载，也不妨碍手动删除。
- 二进制去重不合并业务版本：相同内容的两个版本分别保留反馈、下载和留存记录；实际对象在所有有效版本/引用释放后才删。

### 3.4 关键约束

1. 正式任务与批次一对一，通过批次的任务外键及唯一约束保证；事务内校验一个SKU、一个规格、十位置，`UNIQUE(batch_id, slot_index)`，位置范围1–10。同商品三规格对应三个任务/批次；自由节点记录没有BatchID，可同源不同规格且不参与R0。
2. 一个位置最多一个已排队/执行的生产操作；同一幂等键和相同请求返回原操作，不同内容返回409。模型外部效果不承诺天然恰好一次。
3. 任务级文本调用关联任务/计划，图片调用关联位置，内部试验再关联ExperimentRun；ModelCall使用明确作用域及外键约束，不强迫所有调用都有ItemID。
4. 首次尝试及原首轮成品引用不可替换。修订追加版本，R0结算快照与当前采用数独立。
5. ItemSelection仅引用本位置已采用的CompositeVersion；服务端校验所属位置、资产类型和反馈。底图/蒙版不能作为正式当前采用版，其待定反馈不独立形成完成阻塞。将当前选中版改为待定/弃用时，同事务清除选择并重新评估未决事项，不改变下载权限。
6. 反馈变更、当前选择、位置放弃及完成判断采用任务/位置锁和乐观版本，避免两个成员同时把不同版本设为唯一当前版。
7. 普通历史关联使用不可删除元数据及软引用，真实使用依赖用AssetReference/AssetLease；禁止级联物理删除对象。
8. 生产环境最多一个Active及一个接收灰度流量的Draft；可保存多个未参与灰度的Draft和全部Archive。生命周期状态只有三种，检查/执行结果另用字段。
9. 每用户最多一个当前有效TeamMembership；原创建者字段不可变，当前负责人初始为创建者，个人/团队任务及独立会话失权负责人均可通过专用交接原子变更并记录审计。个人资源修改及个人/团队资源的范围切换均校验当前负责人，团队资源共同编辑不变。
10. Product是团队共享根，其自由画布沿用商品权限；ProductionTask、ImageSession分别作为独立授权根。三类根的整项删除统一记录归档，无正式任务的商品同样适用；不级联归档/取消/删除关联根、资产或文件，不改变已接受操作及留存时钟；归档访问仍逐根鉴权。
11. 不改输入/配置、零新增模型请求的本地恢复关联原Attempt并追加恢复执行记录，不覆盖首次成品。区分暂时阶段失败、等待人工恢复和明确结束首轮；前两者不能提前触发R0结算。
12. 已关闭等待的尝试在任务完成后产生的迟到成品，登记为历史输出并保持默认待定；仅用户明确纳入当前工作后创建当前待处理事项。反馈值本身不隐含该纳入操作。
13. 归档与新操作接受按根资源锁及row_version串行决定。归档前已接受工作继续收尾；归档后的新内容、生成、重试及显式本地恢复拒绝并保留草稿，取消归档后仍须明确提交。普通管理记录及逐图生命周期操作按6.2独立判定，不能统一拒绝所有写请求。

## 4 生产链路、请求与任务状态

### 4.1 事实、文字及合成

商品单图可以启动，但不能证明背面、内部及功能。GPT6输出十条记录，经过字段、数量、事实引用及人工确认后进入图像流程。无动作参考仍传商品原图；有参考只借动作场景构图。参考库使用标签过滤及可解释排序，零匹配明确走无参考分支。

商品展示主图使用独立引用，不能通过改写证据原图的类型来替换。模型输入依据ProductEvidenceVersion解析可核验原图；生成图即使成为展示主图，也保留生成来源且不能被当作商品事实证据。

内容语言字段建议为`content_language`，固定映射中文`zh-CN`、马来语`ms-MY`、印尼语`id-ID`、菲律宾语`fil-PH`，默认`zh-CN`；实际DTO字段名在任务设计中冻结。它独立于界面locale、市场及旧模板的template_language，不从操作者界面语言隐式赋值。文本生成接受显式所选语言，保存预览版本、输入摘要及调用账本；确认绑定该预览的语言、文字版本、操作者和时间。切换语言使新草稿需要重新生成并确认，不覆盖旧快照、不自动调用模型；未确认预览不能进入正式合成。语言生成使用文本模型，人工改字合成保持两类模型零调用，分别统计。渲染按实际文字检查所需字形和溢出。

自由画布“运行全部”只提交自由节点，允许同一来源图连接不同规格的生成节点。正式任务通过独立确认入口读取不可变PlanSnapshot/SlotPlan及资产版本；画布节点的修改、替换或删除不覆盖正式计划，也不隐式启动正式生产。

链路为`确认计划 → 无宣传文字底图 → 目标画布适配 → Pillow精确叠字 → 待定图片`。现有AI生图和模板渲染分支需串接；文本失败不能自动用模板填充冒充GPT6成功。仅改字、字号、颜色或模板参数复用底图，两类模型调用均为零。

字体文件及版本随模板保存，渲染前测量全部字符、字形、换行和高度；缺字、溢出或资源缺失明确报错，不静默截断/换字/换字体。预览及下载引用同一合成版本，不在浏览器另渲染一个不同导出结果。

### 4.2 蒙版、输入与尺寸

蒙版作用于无宣传文字底图；预览坐标转真实像素前处理方向和缩放，图像与蒙版统一同尺寸PNG、Alpha透明区表示待编辑，明确首张输入及蒙版对象。产品25MB限额与模型更严格限制共同校验。模型蒙版只是编辑引导，区域外是否保持必须看实际结果。[官方图像编辑说明](https://developers.openai.com/api/docs/guides/image-generation)

记录模型原生尺寸和最终画布尺寸，9:16绝对像素待打样冻结；1200×1200和800×800由适配及合成得到独立文件，不要求模型直接原生返回每一种最终尺寸。等比例缩放、留白或确认的适配方式不能拉伸或裁掉关键结构。生成登记时解码校验格式/尺寸，下载时检查对应对象大小/摘要等元数据；完整尺寸与视觉正确性另由验收确认，不因人工弃用禁止下载。

### 4.3 不隐式补发模型请求

业务操作和Outbox在同一短事务写入；投递器允许重复发送消息，worker通过数据库原子领取同一StageExecution避免重复执行。可能已经跨过外部请求边界的步骤不得恢复为未派发。

```text
未派发 → 领取并持久化派发意图/配额占用 → 单次外部请求
                                           ├─ 有确定结果 → 结果与费用登记
                                           ├─ 明确失败   → 等用户重试/放弃
                                           └─ 崩溃/超时 → 结果未知，查询原请求或人工处置
```

派发意图持久化与实际网络发送之间存在无法原子化的窗口；恢复时宁可保留未知，不自动补发。provider如有可信结果查询接口可查询原请求，查询不能创造新的生成请求。接受用户显式重试模型请求才新建OperationID/AttemptID，并提示未知原请求可能已收费；原底图和确认输入/配置不变的本地恢复按4.5保留原尝试归属。

操作接受事务校验当时的当前权限，保存accepted_at、提交者和根资源/范围/版本等授权依据，再同事务写入Outbox。后续用户禁用、离队或失权阻止新提交，不撤销此前已接受操作及其已确认阶段的执行许可；worker继续检查接受记录、取消顺序、配额、输入可用性及ReleaseID，不能用历史许可接受新操作。显式取消由当前有修改权者发起，已有取消与派发锁规则优先执行；原提交者和接受时记录不因交接被覆盖。

SDK显式设`max_retries=0`，HTTP代理/网关、provider参数降级与后备模型、队列重试及启动恢复均审计到实际网络派发层。接入时核查所安装SDK的重试配置，并确保实际请求链关闭隐式付费重试。[官方SDK重试说明](https://github.com/openai/openai-python#retries)

每次实际模型请求记录ModelCall及占用，不因拒绝/失败/超时退回原型额度；重复结果不能重复入账，但账本幂等不等于保证外部服务从未重复计费。原型全局12次额度归ExperimentRun，跨重启、任务及复制共享，`n=1`串行；文本另计。未满足放行条件时先诊断并提出针对性验证方案；需要新真实调用时，明确目的、样本、参数、判断标准和次数，经用户确认后另建关联实验，保留原额度及首轮结果。新ExperimentRun不能用来绕过本轮额度。生产模型并发按实际请求跨新旧worker统一控制，Pillow另设本地容量。

### 4.4 九状态与取消

业务状态保持草稿、待生成确认、生成中、待成品确认、修改中、处理异常、已完成、取消中、已取消。草稿允许文本准备，文本排队、生成、失败作为Operation技术进度，十份计划校验通过后进入待生成确认。图像生产提交后的聚合优先顺序为已接受取消及其收尾 → 初次生产操作是否排队在途 → 修订是否排队在途 → 是否存在可处理候选/未决问题 → 是否满足完成条件。

部分图片就绪时可反馈、下载及明确发起修订。同一位置最多一个排队/执行操作；当前生产轮未结束且新操作准入仍开放时，提前修订追加独立操作/尝试及输入快照，沿用当前轮ReleaseID。旧版本退出后按7.4停止追加，新修改保留草稿。仍有初次操作排队/运行则主状态为生成中；初次全部结束后若仍有修订在途，则为修改中。

取消和派发意图使用同一任务锁决定接受顺序。取消前已获准派发的步骤属于在途；取消接受后不再批准后续生成、重试或合成。没有在途步骤直接已取消；有在途则取消中，全部返回或各自有限deadline后终结。独立恢复扫描器处理失联worker，不能仅靠worker内部计时。

已取消任务的迟到结果以原AttemptID入档，图片默认待定，不复活任务、不切当前采用版、不触发后续合成。完整图与中间底图按类型明确展示，均可按权限和生命周期下载。任务取消不等于图片删除。已取消继续生产须复制新任务/批次并重新确认，已完成可在原任务追加修订；未取消任务的迟到底图按4.5由用户明确发起补合成，不因登记结果自动执行。

### 4.5 完成与首轮统计

完成条件为十位置均有明确当前采用的合成成品或位置放弃，且当前工作无排队/执行、未处理成品候选、尚未处置的未知问题或其他未决事项。底图/蒙版的待定反馈不独立阻塞完成，执行失败仍须处置。用户明确结束对未知结果的等待后，关闭相应未决事项，原未知Attempt与待核对费用继续保留，不因这些历史记录阻止业务收尾；后续模型重试仍须明确新操作。6个采用加4个位置放弃、甚至全部放弃均可完成；弃用一个候选不自动放弃位置。自然过期只改变文件状态，不倒改历史完成事件。

已完成任务收到此前已关闭等待的尝试的迟到成品时，保存历史输出及默认待定反馈，但不自动创建当前候选OpenIssue，不重开任务或切当前选择。用户明确纳入当前工作时，按当前权限、幂等键、任务/位置锁及row_version建立纳入记录，再重新聚合任务状态。历史反馈和未结算首轮独立处理，不把采用反馈等同于纳入当前工作。

完整首轮的`R0 = 原首轮采用位置数/10`，失败仍计分母；未执行位置使评估不完整，待定不算采用。所有原始位置及反馈处置完整后结算，保存Q01–Q09及反馈快照。后续修复、当前选择、删除和反馈修改不倒改快照，纠错另加修订记录。自由节点、打样、修复和混SKU探索不填入分母。R0与任务完成、图片下载均独立，内部R_trial不替代正式批次效果证据。

首次执行结论按端到端产出判断：取消时只有成功底图、没有原CompositeVersion且没有明确首次失败结论的位置，记录为中断/不完整，不根据ModelCall成功把该位置补成“已执行未采用”。十底图、七成品采用、三位置合成前取消不允许结算最终7/10；明确首次失败仍计分母。取消后的可靠原结果核对可以补齐未结算结论，但不能启动新合成或用新尝试替代原结果。

首次尝试可使用新生或复用底图，必须逐位置保存来源类型和源版本。复用底图按本批确认计划首次合成的成品可计本批R0；不能继承源反馈或把旧成品直接当本批首次结果。报告按来源汇总，复用成绩不证明新生图效果，原型仍需十个独立首轮。

结束未知等待不把未知改成失败。可靠核对的原首次尝试迟到结果可补齐未结算评估，十位置结论及原合成成品反馈齐备才结算；只有底图不足计采用。重试/修复不替换原首次尝试，已结算快照不自动改写。统计补齐不取消终态或授权已取消任务继续合成。

本地恢复和迟到底图补合成使用以下契约：

- 首次底图成功后的合成/存储暂时错误，保持原Attempt及输入、文字、模板、字体、布局等配置摘要；追加阶段恢复记录，全部模型调用计数增量为零。可恢复阶段尚未终结时不结算该位置，成功登记的首个原成品仍可进入首轮。
- 每次恢复执行有有限deadline，由独立扫描器停止超时自动恢复，按执行领取/租约契约终结本次技术执行并留下待处理业务事项；等待人工本身不保持旧轮在途，也不延长旧worker驻留。当前有修改权者显式选择继续或结束；继续需新的恢复执行记录和有限deadline，结束则保存本地首次失败结论，后续修复不得替换原首轮。外部未知请求仍保留未知和待核对费用。
- 原首次尝试的迟到底图仅在任务未取消、首轮未结算、尚缺原成品、未被明确结束为本地首轮失败、输入/配置可验证且用户明确确认时补合成。同位置已有排队/执行操作时返回冲突并保留草稿，不另外排入竞争操作；已完成任务须显式纳入当前工作。仅补本地合成及结果登记，不重新请求模型。
- 恢复记录保留原尝试溯源和实际执行轮/ReleaseID；恢复在原轮内时沿用该轮版本，原轮结束后的显式本地恢复按7.4建立兼容执行身份，原尝试的ReleaseID及首轮引用不改写。新版本必须验证能够执行相同输入及渲染配置，否则保留待处理原因，不能通过改输入或补发模型请求冒充原首轮恢复。
- 取消、版本退出准入、幂等、文件恢复授权、引用/租约及当前选择规则同样适用；最终结算快照不接受后续回填。

## 5 详细设计一：图片反馈、下载与MinIO生命周期

### 5.1 反馈与当前选择

每个图片版本默认待定。反馈接口接受`feedback, reason, expected_version`，记录FeedbackEvent并更新当前值；保存用户、时间、旧值及新值。仅具备任务修改权的用户能操作，同团队只读成员仍可下载。

批次选择当前采用版使用独立操作，或在“采用并设为当前”中同事务完成；只接受本位置已采用的合成成品。仅历史留档的迟到版本须由用户明确纳入当前工作，才能参与当前选择；单独修改历史反馈不隐含纳入。新图采用前不自动覆盖旧选择；旧图被取消采用时清除其选择并提示该位置仍需处理。对自由节点只保存逐版本反馈，不强制创建批次或位置。

撤回已生成的待定修订成品时，同事务写入弃用FeedbackEvent、关闭该候选事项并重新聚合完成条件；保留原当前采用版及历史，不删除字节、不追加模型调用、不产生“撤回但仍待定”的历史类别。使用当前权限、幂等键、任务/位置锁及expected_version，其他成员已改变选择时返回冲突，不静默切回旧版本。未提交草稿可直接撤销；此操作不代替取消已接受工作。

反馈、下载、删除互不隐含触发：弃用不删除不重试；采用不等于成功下载不永久保留；下载不自动采用；删除及恢复保留反馈历史。图片在回收站/已清理时，授权用户仍可调整反馈、撤销选择和关闭未决事项；事务检查权限、row_version及业务状态，已结算统计不变。图像文件修改另校验输入可用性，回收站依赖按5.4经用户确认恢复后才可使用，已清理文件不能恢复。

### 5.2 存储访问与成功下载判定

统一StoragePort提供`put, head, open_stream, delete`等接口。对象键采用环境/团队/资源/不可变版本及随机标识，不从用户文件名拼可遍历路径。私有bucket，凭据仅服务端持有；数据库保存实际对象键和SHA-256、格式、尺寸及大小。对象键不覆盖旧版本。

下载流程：

1. 根据图片版本找到根资源，检查当前登录、团队可见性及`lifecycle=live`；反馈值不参加授权。
2. 在短事务创建DownloadEvent和有截止时间的AssetLease，锁定具体对象版本，防止下载期间被清理。
3. 由认证文件服务完整流式传输，设置正确长度、文件名及资产类型。预览接口与下载接口明确分开，不让预览或预签名URL创建动作算下载。
4. 传输正常结束且字节完整、没有可观察的断开/错误后记录`completed_at, bytes_sent, file_hash`，幂等设置该图片版本`first_downloaded_at`。记录失败、部分或未确认完成的传输，不伪造成功。
5. 释放租约，重算到期资格；系统记录完整传输不承诺浏览器已经写入用户磁盘。若传输完成后记录失败，使用可持久核对的传输事件补记，未核对前保持清理保护并报警，不能仅因点击下载永久保留。

首期使用受控完整下载；若以后支持Range/分片，只有同一DownloadID覆盖完整对象且完成确认才算成功。不能让直连MinIO、公有URL、旧FileResponse路由绕开下载账本。服务可按负载优化流式传输，但必须保留上述授权、完成及失败语义。

一个版本被任一有权限用户成功下载即获得长期保留；相同底图重生成或改字产生的另一版本独立计算。手动删除与下载同时发生时，以数据库事件顺序为准：已接受的传输可结束并记账，但不能撤销后来明确的手动删除。

### 5.3 生命周期规则

| 条件 | 到期/处理规则 |
| --- | --- |
| 生成图片未下载、非历史保护、正常区 | `retention_started_at + 30天`到期自动入回收站 |
| 生成图跨资源复用的新记录 | `retention_started_at=reused_at`，新30天；保留原生成时间，反馈初始待定，不继承源下载标记 |
| 成功下载过该版本、正常区 | 不自动到期，直到用户手动删除 |
| 历史下载情况不明 | `legacy_protected=true`，不自动到期；支持手动删除 |
| 手动删除任意正常区图片 | `trashed`，`trash_reason=manual`，`purge_after=deleted_at+7天` |
| 未下载正常期到期 | `trashed`，`trash_reason=expired`，入站时重新计算7天，不从原生成日倒推缩短 |
| 回收站恢复未下载图片 | `live`，保存`restored_at`，`retention_started_at=restored_at`，新30天 |
| 回收站恢复已下载图片 | `live`且保留`first_downloaded_at`，至手动删除 |
| 历史保护图片恢复 | 保留历史保护；恢复不伪造下载记录 |
| 回收站超过7天但字节尚存且无清理claim | 仍允许有恢复权的用户恢复；超期不保证文件继续存在 |
| 回收站7天已到且无有效引用/租约 | 幂等清理对象，最后写`purged`及审计事件 |

在自动过期事务中复查下载事件及有效下载租约，避免下载正要完成却先过期。反馈待定/采用/弃用完全不改变到期计算。文件没有被用户删除不等于无限保留，已确认的新政策优先于旧文档“至少7天”通用表述。

### 5.4 引用分类和安全清理

AssetReference至少区分：历史溯源软引用、正常区资产的编辑依赖、活动任务输入、共享素材引用。AssetLease用于在途生成、合成、下载和迁移的临时保护。活动任务或其他编辑任务引用的文件，即使入回收站仍不能物理清理；普通历史行和单纯采用标记不构成永久保护。

可继续编辑的正常区成品保护其底图、蒙版、字体等必要依赖的字节，删除/到期后按依赖关闭或仍存活的其他资源重新计算。保护释放不重启回收站7天期限。首次登记使用显式引用关系，不能只靠全库字符串扫描或单个引用计数判断安全。新任务从回收站取图须先恢复；已开始的任务可凭已授予的输入租约读完，该租约不授权后续新的文件修改。

用户修改成品时，前后端检查必要依赖的生命周期。底图在回收站则在当前入口列明所需恢复图片，用户确认后调用受控恢复操作，系统原地恢复，无需用户前往回收站查找。后端仍校验每个依赖的恢复权限、预期版本、文件存在及清理claim；只有恢复成功且输入可用才允许继续修改。用户拒绝时提示“不恢复所需图片，当前成品图无法修改”；恢复失败、无权限或已清理时显示具体原因并阻止文件修改。不得未经确认恢复、因引用保护绕过trashed检查或触发模型请求。

收藏仅保存源版本关联，反馈、下载和留存沿源版本。跨根资源复用则保存目标根的新业务版本和源版本关系，校验同团队源查看/下载权、源版本live且可用、目标修改权；不能要求只读用户具备源任务修改权，也不因此允许整任务复制。源记录与目标记录的反馈、下载、删除和到期相互独立；新记录按复用时间计30天，不继承下载标记。物理文件可共用，清理须复查所有有效版本及依赖，删除目标记录不连带删除源记录。

分层成品复用必须保留可编辑结构。事务接受前解析成品的必要依赖图，对成品及底图、蒙版、字体/模板版本等逐项验证可读、可用和清理claim；源依赖处于回收站时先按权限确认恢复，缺失或无恢复权限时阻止可编辑复用，不静默扁平化。目标侧建立独立成品/生成图片记录、文字与布局快照、依赖引用及源到目标映射，禁止新成品继续以源个人任务的业务资产作为唯一编辑依赖。目标侧属于生成图片的成品、底图/蒙版新记录分别从复用成功起计30天且不继承下载标记；上传证据、共享参考、字体/模板仍按资源依赖规则保护。

目标记录和完整依赖关系全部登记成功后才报告复用成功，失败不能留下表面可编辑却缺依赖的成品；建立引用与GC互斥。不可变文件可去重共享，目标负责人按目标权限操作目标记录，源删除不使目标入回收站，目标删除也不影响源。复用不调用模型、不继承源采用或首轮成绩；正式首轮仍要求按本批确认计划产生首次合成。

清理采用数据库领取与幂等状态机：

1. 选取回收站超过7天的候选，按对象加锁，复查所有共享版本、引用、下载及活动租约，记录清理代数/claim。
2. 标记内部`purge_in_progress`，阻止新的引用、下载及恢复同时成功；它是执行字段，不新增用户生命周期状态。此时恢复返回清理进行中，不能先显示恢复成功后又删除对象。
3. 删除MinIO对象；失败保留可重试工作项，不先把数据库写成已删除。所有删除尝试只操作同一不可变键，绝不触发模型请求。
4. 对同一claim确认删除或已不存在后，写`purged`并保留元数据/反馈/费用/首轮快照；进程崩溃由扫描器结合对象HEAD核对后继续。

恢复事务在清理claim取得前成功则清理资格失效；claim取得后不能未经协调改回live。引用创建也检查claim，以免清理复查后又插入新引用。对象去重时任一仍有效的版本均阻止删共享字节。

不对业务图片bucket配置会跳过数据库引用及下载状态的统一年龄TTL。可以清理未完成上传的临时对象，但须使用独立临时前缀/登记和保护期限，不与正常图片混用。GC失败重试是文件操作，与禁止模型自动重试无关。

### 5.5 上传、结果登记与旧图迁移

对象写入与数据库不是同一事务：先登记上传意图，再写不可变对象并校验，最后短事务登记AssetFile/版本/引用并标可读。中途崩溃由孤儿对象扫描和上传意图恢复，不重复请求模型来弥补存储失败。商品原图、共享参考、字体及模板按资源生命周期保护，不套用生成图片的未下载30天计时。

迁移步骤：

1. 盘点商品图、会话结果、图库、poster引用、参考复制、蒙版及JSON字段，建立文件到全部业务引用的映射；核对共享文件与独立复制文件。
2. 为旧资源补根任务/团队/归属及AssetReference。归属不明先隔离，不把所有图片公开或默认为所有人可见。
3. 写入MinIO，核对大小、SHA-256、解码尺寸及抽样读取；只有对象验证成功才切该条storage_backend/key。
4. 旧下载历史不明的版本标历史保护，原时间和来源保留，不设虚假的first_downloaded_at。
5. 迁移期统一读取接口按每条storage_backend路由；旧本地文件只读保留作核对，不在迁移切换中顺手删除。
6. 先发布可读LocalStorage及MinIO的兼容基线，验证回滚，再逐步切写入MinIO；仅懂本地路径的版本标记不可回滚。旧文件最终清理单独按引用及迁移验收结果执行。

## 6 详细设计二：独立身份、团队权限与审计

### 6.1 账号及会话

系统级管理创建独立用户名并分配角色和一个当前有效团队，使用成熟密码哈希库，不存明文密码。MVP不提供多团队切换或团队级管理员；系统管理能力不扩大业务资源访问范围。首次凭据交付及密码重置使用一次性凭据，正常入口HTTPS；会话只关联稳定UserID，不把角色/团队的旧快照当长期授权。企业SSO将来通过身份映射接入同一UserID体系，本期不接入。

管理可启停用户和成员关系；停用、密码重置或重要授权变更递增session_version/撤销会话。每次敏感操作核对当前启停与成员关系。原共享管理口令及设置解锁不能在生产保留为绕过新权限的平行入口。

首次管理账号由部署初始化明确创建，其后的账号维护走审计接口。日志不记录密码、模型密钥、存储密钥或完整会话令牌。

### 6.2 授权决策

统一函数`authorize(user, action, root_resource)`先检查登录/启用，再检查当前TeamMembership、任务范围及动作。所有文件/预览/图库/下载、反馈历史、任务复制及引用操作均追溯根资源，不能仅凭随机ID当授权。

Product及其自由DAG采用团队共享编辑；ProductionTask和独立ImageSession分别保存TeamID、scope、created_by_user_id、responsible_user_id并按自身根授权。会话创建明确选择个人/团队范围，不从挂回商品目标继承权限。所有商品、任务及独立会话的整项删除只更新根归档标记、操作者和时间，禁止复用原整树删除路径；关联根及图片/历史仍有可访问入口且各自鉴权，原留存规则与执行状态不改变。

归档允许在排队/执行中接受，worker按原接受记录完成既定阶段，结果登记不因根已归档而丢弃。归档界面仍可查看进度和结果；有原修改权者可反馈、处理选择及未决事项、取消、逐图删除/恢复。新内容编辑、生成、重试或显式新本地恢复必须先取消归档，接口返回明确状态冲突并保留草稿。取消归档仍检查当前权限、幂等及版本，只恢复根入口和准入资格，不联动图片恢复/留存、不改任务主状态、不复活已取消任务或自动提交草稿。关联独立根不继承上级归档限制。

| 能力 | 当前规则 |
| --- | --- |
| 商品资料及自由画布编辑 | 当前同团队成员共同编辑；不传递关联个人任务或会话修改权 |
| 商品/任务/独立会话整项删除及取消归档 | 按各自修改权限记录根归档/取消归档；图片独立留存，不级联归档、取消或删除关联根 |
| 归档中管理与新生产 | 已接受阶段继续；按原权限允许读/下载、反馈/选择处置、取消及逐图管理；新内容/生产须先取消归档 |
| 同团队查看及下载 | 个人或团队任务均允许；反馈不参与判定 |
| 修改个人任务 | 仅当前负责人，初始为创建者；包括反馈、生产、重试、取消、复制整个任务、删除、恢复 |
| 修改团队任务 | 当前团队成员；实际操作人分别记录 |
| 修改共享范围 | 仅当前负责人，权限随专用交接移交；团队变个人后其他成员旧会话不再可写 |
| 单图跨根资源复用 | 同团队源查看/下载权、源正常可用及目标修改权；创建目标独立记录，不授予源修改或整个个人任务复制权 |
| 跨团队访问 | 拒绝，包括知道对象键、历史ID或复用旧下载请求 |
| 账号/团队/共享库管理 | 系统级管理角色；不自动授予他人个人任务普通修改权 |
| 完整设置、provider档案/绑定、配置导入导出 | 当前系统管理角色且独立设置已解锁，两者缺一即拒绝；读取/预览/导出不回传已保存密钥 |
| 日常运行时能力与规格读取 | 正常业务账号可读脱敏必要字段；不返回完整配置、密钥或受限资源数据 |
| 失权个人/团队任务及会话交接 | 管理专用操作；原负责人已停用或离队，接收者为资源所属团队的有效成员；原创建者、TeamID及scope不变 |
| 发布、灰度、激活、回滚 | 管理角色，并满足发布状态及检查前置条件 |

系统清理和备份使用限定职责的服务身份，记录service_actor及触发原因，不借此提供“管理可任意编辑个人任务”的业务通道。管理将用户移出团队后，该用户也不能仅靠“曾经创建”继续读取或修改该团队资源。

任务及会话至少区分不可变`created_by_user_id`与可交接`responsible_user_id`（建议名称）。交接短事务内核对管理角色、原负责人失权状态、接收者当前启用及同队关系、expected_version和幂等键，再更新负责人并写AuditEvent；记录原因、前后负责人及执行者。个人资源修改权与负责人身份移交，个人/团队资源的范围切换权随负责人移交，团队共同编辑不变。原创建者重新启用也不自动收回权限。交接保留TeamID、范围、历史、费用及首轮快照，不自动派发新生产或恢复文件。

会话撤销与已接受执行许可分开处理：账号或成员关系变更立即影响新请求的权限，后台继续执行撤权前已合法接受的工作，按4.3核对接受记录及快照。当前有修改权者可以显式取消；管理交接不能伪装成原用户的新提交，撤权也不自动把存量操作改记取消或失败。

设置入口及其读取/写入/预览/导出接口逐次检查当前管理角色与独立解锁状态，旧解锁标记不能绕过撤权。设置导出只含非密钥配置及必要的凭据配置状态；旧导出包含provider原始api_key的契约不作为二开目标。接收授权提供的密钥输入与回传已保存密钥分开处理，预览仅给存在性/计数等脱敏信息；导入缺失密钥时不得伪报目标provider已可调用，实际补配及校验纳入迁移契约。

### 6.3 并发、审计与历史迁移

写操作携带预期row_version，事务中同时校验权限、版本、对象状态；冲突返回409及当前版本，前端保留编辑草稿供用户重新核对。反馈、删除/恢复、范围修改和当前版选择同样受保护，不能只给文案保存加锁。

AuditEvent记录UserID/服务身份、TeamID、动作、资源/操作/发布ID、前后版本、事件时间及结果。DownloadEvent另记下载传输，反馈另记FeedbackEvent；它们都引用同一稳定UserID。写操作不能因灰度转组改变归属或审计身份。

旧资料没有归属时由迁移清单明确映射团队及适用的范围/负责人，未经映射保持不可公开访问；不能默认为所有人可写。管理完成账号配置不等于允许接管其他个人任务，个人/团队任务及独立会话失权负责人须经过6.2的专用交接。现有业务数据先备份并演练迁移，保留原数据及映射证据。

建议管理接口为`POST /admin/users`、`PATCH /admin/users/{id}`、`PUT /admin/teams/{id}/members/{user_id}`、`POST /auth/login`、`POST /auth/logout`；任务范围变更用`PATCH /tasks/{id}/scope`。具体命名可沿用仓库风格，服务端授权语义不能被简化。

## 7 详细设计三：软件发布、灰度、回滚与运行保障

### 7.1 环境及发布包

测试和生产分别使用数据库、Redis实例/队列及MinIO空间和凭据，默认不能互相访问写入。生产独立服务器，测试可使用现有开发机或另一环境。备份位于生产服务器之外，不把同机另一目录视为异机备份。

ReleaseVersion为不可变发布包：`release_id, source_commit, frontend_digest, backend_digest, worker_digest, dependency_lock_digest, schema_compat_range, config_schema_version, object_contract_version, queue_payload_version, test_report_id, state`。密钥仅引用独立配置，不进入包和日志。修改代码、配置契约或依赖产生新ReleaseID，不覆盖已测试发布包。

EnvironmentDeployment保存环境、稳定版、候选版、灰度比例、分流salt/代数、期望路由及实际就绪路由；发布检查报告记录当前数据库、对象协议和在途任务协议。构建归档不含业务数据快照，软件Archive与图片回收站无关联。

### 7.2 三状态及操作

| 状态/操作 | 流量和前置条件 | 结果 |
| --- | --- | --- |
| Draft入生产 | 测试清单通过，兼容及依赖检查通过 | 注册候选；尚未开灰度时0新流量 |
| Draft开灰度 | 管理操作、固定用户分组、资源容量足够 | 候选约20%用户，Active约80%；保持Draft |
| Draft停止灰度 | 管理根据故障操作 | 候选0新流量，稳定版100%；候选仍Draft或由管理归档 |
| Draft激活 | 至少1工作日、核心覆盖、无阻断问题，管理人工确认 | 候选Active，旧Active变Archive，所有新流量切新版本 |
| Archive回滚 | 管理操作，当前兼容检查通过，目标已就绪 | 目标Active，原Active变Archive，业务数据不回退 |
| Draft归档 | 候选放弃且不再接新流量 | 进入Archive，保留包和失败/放弃原因 |

Archive默认不接新业务流量，但其已启动任务可继续由保留worker收尾。操作执行中/失败、测试通过/失败、灰度运行与否都用独立字段记录，不增加第四种发布生命周期状态。

工程初始化建议：首次生产尚无Active时，仍以Draft只开放约20%的固定试用账号，其余账号暂不开放生产；满足相同观察和人工激活条件后才全量开放。停止首次灰度则回到生产未开放状态，不虚构一个可回滚历史版。首次激活前在测试环境用已登记的兼容构建演练切换/回滚机制；随后真实生产历史版才逐步形成。

### 7.3 固定用户约20%分流

用户登录后由可信身份层获取UserID，采用`hash(release_id + fixed_salt + user_id)`分桶，并持久化CanaryAssignment；阈值约20%。同次灰度salt固定，用户请求/刷新/重登录不重新抽签；小样本人群展示实际人数比例，不承诺每分钟请求量恰好20%。不得用内网IP、共享口令或前端可篡改的header代替UserID。

Nginx负责代理，发布/身份层计算或验证分组，前端静态资源和API保持协议兼容。Nginx的split_clients本身可按输入字符串哈希分组，但不负责登录身份、业务任务固定版本或人工激活；若使用它，输入须来自可信UserID而非直接套用按IP示例。[Nginx官方说明](https://nginx.org/en/docs/http/ngx_http_split_clients_module.html)

共享任务的不同用户可以属于不同版本，读取/写入协议必须兼容；后台已启动的生产执行固定ReleaseID，不因为另一成员打开页面而切worker。旧前端标签页仍须在兼容窗口内工作，跨版本不兼容请求应明确提示刷新，不能误派发模型请求。

### 7.4 每轮执行与队列固定版本

每轮执行对应一次明确接受的批次生产或修订工作，保存ReleaseID及输入快照；子操作、尚未派发的位置和后续处理阶段沿用该版本。任务历史不永久绑定某版：当前轮所有已接受操作结束、必要收尾完成后，用户在原任务明确发起的新修订经输入与协议兼容检查，可采用其当前分流版本，并记录新的执行身份和ReleaseID。原Task、Item、历史输入、费用及首轮统计不改写。已取消任务复制后，按新任务首次执行时的当前分流选择版本，不继承源执行或达标结论。自由节点执行同样固定版本。

当前生产轮尚未结束且对应版本仍接受新操作时，允许已就绪位置提前修订，修订追加独立Operation/Attempt及确认快照并归属当前轮ReleaseID，不按修订操作者的灰度分组切换软件版本。同位置活动操作互斥；原首轮尝试和计划不被修订覆盖。全部已接受操作及必要收尾完成后，新一轮才可按当前分流选择兼容版本。

切版或停止灰度使旧版本开始退出时，关闭该版本旧轮的新操作准入并记录关闭时间/代数，固定已接受工作集合；接受操作和关闭准入必须串行判定，避免切换后继续追加。旧worker只执行关闭前已接受操作及其既定后续阶段，仍受取消、配额及有限截止约束。关闭后的新修订、本地恢复或迟到补合成请求保留为草稿/待处理，不追加到退出中的旧轮；旧轮收尾后由当前有权用户重新确认新轮，经兼容检查选择当前分流版本，禁止自动提交草稿。恢复仍可按4.5关联原尝试，不能因此重新打开旧轮准入。

消息使用环境及版本队列，如`prod.release.<id>.image`，载荷含operation/attempt/stage/release/payload_version；worker领取时校验版本，不能只靠队列名信任消息。新旧worker共享数据库调用账本、全局配额和原型ExperimentRun额度；消息重投不等于重新发模型请求。

激活/回滚停止旧版新流量后保留旧worker与必要API协议，直到其排队执行及在途步骤终结。严重基础设施故障导致旧链无法安全继续时，发布操作可停止该执行器接收后续步骤，由恢复扫描器记录基础设施中止、未执行位置和结果未知，任务按规则进入待处理状态；这不授予管理修改他人个人任务或代发业务取消的权限。不会把原执行自动搬到新版本重新生成。每步有限deadline加独立恢复扫描器，避免归档worker永久占用；确认无仍应执行的工作后停止常驻进程、保留归档构建。迟到结果仍按原Attempt归档，不能因为旧进程停止而新建付费请求。

### 7.5 灰度门槛和操作接口

开灰度前：对应P0测试通过、依赖就绪、双版本兼容、迁移完成、备份可恢复且容量可同时容纳两版。灰度报告至少包括观察开始/结束、工作日历、分组人数、上传/生成/反馈/下载/删除/恢复覆盖，失败率、时延、队列等待、模型请求/费用异常及数据一致性结果。

激活至少满足1个工作日有效观察且核心操作均覆盖，没有数据丢失、越权、重复付费或关键流程阻断；风险未核实不能标绿。没有自动倒计时激活，管理点击后还须服务端重新校验同一ReleaseID的证据和当前部署代数。

重复付费检查关注同一操作被非预期重复派发或收费；用户知情确认的新尝试独立记录费用，不能用同一幂等键掩盖两次实际请求，也不能将费用未知直接视为检查通过。

| 建议接口 | 前置/行为 |
| --- | --- |
| `POST /admin/releases` | 注册经过测试的不可变发布包，生产初始Draft |
| `POST /admin/releases/{id}/canary` | 校验兼容/就绪，按固定用户开启20%灰度 |
| `POST /admin/releases/{id}/stop-canary` | 停候选新流量，保留数据及在途收尾 |
| `POST /admin/releases/{id}/activate` | 管理角色、证据达标、expected_deployment_version |
| `POST /admin/releases/{id}/rollback` | 目标Archive兼容、依赖就绪、明确目标和原因 |
| `GET /admin/releases/{id}/report` | 测试、灰度、兼容、在途和操作结果 |

所有改变发布的请求使用幂等键和部署乐观锁。API只提交受控发布操作，不允许用户传任意shell命令或未经登记的构建标签。

### 7.6 激活及回滚的一致性

发布控制器先准备目标实例并校验就绪，再生成新的路由generation；数据库事务更新期望Active/Archive、稳定/候选和ReleaseEvent，入口应用完整generation后回报实际生效状态。因数据库与代理配置不能原子提交，控制器必须比较desired/observed并重试同一幂等配置，UI不能在路由未生效时报告切换完成。

切换期间使用完整版本化配置，入口要么采用旧generation要么新generation，不能部分API指向候选而文件服务绕开权限。失败时保留明确的“发布操作失败/未生效”记录和原可服务入口，恢复路由与状态一致后再接受下一次切换；不得同时向两个发布者开放竞争操作。

回滚检查至少覆盖：当前schema读写、新枚举及字段处理、MinIO对象键与存储后端、账号/权限、下载留存字段、队列载荷、配置及正在执行的旧链。记录检查针对的数据库迁移号、存储契约和队列版本，环境变化使旧报告失效。

回滚操作只换前端/后端/worker及兼容配置，不运行旧数据库快照恢复、不倒退业务数据。保留候选期间产生的图片、反馈、任务、调用和费用；若归档程序不会读取这些字段/对象，阻止回滚并展示具体不兼容原因。所有Archive保留，但可回滚资格可以随数据库演进变化。

### 7.7 数据库迁移与就绪

迁移由单独受控部署步骤执行一次，不能让每个新旧API实例启动时都执行`alembic upgrade head`。先扩展兼容字段/表、补数据、再切代码；移除旧字段等破坏性操作须在相关历史版本已明确不具回滚资格、在途链清空并演练后执行。Alembic有downgrade文件不等于回退安全，普通回滚不运行破坏性downgrade。

区分存活与就绪：存活检查进程，业务就绪检查数据库连接及schema、Redis、MinIO读写探针、目标ReleaseID worker和所需字体/模板/配置。探针放隔离测试前缀并清理，不调用付费模型。关键依赖不就绪即不接新生产流量，监控显示具体失败组件，不能只有静态`{"status":"ok"}`。

### 7.8 备份和灾难恢复

目标：**RPO≤24小时，RTO≤4小时；数据库和MinIO备份异机保存30天**。备份、软件版本归档和图片回收站各自独立；普通版本回滚保留全部业务数据，只有故障灾难恢复可能损失最近恢复点之后的数据。

建议PostgreSQL采用周期基础备份加连续WAL归档到异机，MinIO不可变对象进行持续或定时增量备份，并生成共同恢复点manifest。基础备份与WAL能够组成数据库时间点恢复，`pg_dump`不能直接当作WAL恢复的基础备份。[PostgreSQL 16官方说明](https://www.postgresql.org/docs/16/continuous-archiving.html)

联合恢复点建立过程：

1. 先设物理清理屏障，选择屏障建立之后的目标WAL位置（LSN）并等待其归档；在隔离备份实例恢复到该LSN，从该实例导出AssetFile/引用/删除标记、配置与发布记录。这样数据库恢复内容与manifest来自同一恢复点，不能把在线MVCC快照和相近墙钟时间当作天然一致。
2. 将manifest中该恢复点仍应存在的对象按键和SHA-256复制/核对到异机；已物理清理的历史版本仅保留墓碑，不要求恢复其字节。必需对象复制完成或建立可靠保护副本前保持GC屏障/备份引用，防止生产随后删除造成备份缺件；业务逻辑删除仍可正常记录。
3. 只有数据库可恢复且全部必要对象齐备时才将BackupSet标为可恢复；最后可恢复联合时间点距离当前不得超过24小时。备份任务启动成功不等于RPO达标。
4. 备份保留30天，数据库链依赖及对象共享副本不能提前清掉；轮转前验证剩余集合仍可恢复。业务已删除对象可能暂存于备份，按备份30天期限退出，不因普通图库查询重新可见。

演练在隔离环境恢复数据库、对象、权限及配置，验证上传/查看/反馈/下载/回收站主流程和抽样完整性，再测服务就绪耗时；真实生成验证按受控计划计费，演练重放不得自动重发历史模型请求。

灾备回退不同于保留最新数据库的进程恢复：备份中的queued/未派发记录可能在恢复点之后已经实际调用，ExperimentRun及生产额度也可能已经消耗。恢复时先隔离可能受回退影响的模型执行、Outbox投递和额度，不能只按旧状态重建可派发队列。结合未随该快照回退的可信派发/额度证据或提供方原请求记录核对；只有可证明未派发且额度核实的工作才可恢复投递，无法证明则保留未知及待核对费用，等待明确处置。提供方查询无结果不直接证明从未派发；不得用恢复旧计数释放已用额度，显式新尝试仍需核实剩余额度。非模型的本地恢复可按幂等契约继续，不能转入付费请求链。

RTO从服务中断发生（演练时为宣布故障的时刻）开始计到服务就绪且核心业务及数据完整性检查通过，包含发现故障、取备份、恢复、配置和校验，不只计算数据库导入。依据实测数据量、网络和存储吞吐验证4小时；没有成功演练不宣称达标。恢复报告记录实际RPO/RTO、缺失对象、故障步骤和整改项。

### 7.9 容量及观测

至少20人混合操作，含2名高频设计；覆盖保存、生成提交、反馈、下载、删除恢复和取消，检查串图、越权、版本冲突、队列等待及资源占用。灰度双版本和迁移期间另测内存/CPU/连接池与下载带宽，不能把20人等同20路图像请求。

容量估算依据实测日生成量、平均对象大小、底图/成品/蒙版数量、已下载比例、历史保护量、回收站、备份及增长率。已下载可长期保存，不能简单按37天推算全部存储容量。空间不足时先告警、拒绝无法持久化的新任务，不自动删除受保护历史或付费重生图。

日志串联TaskID/BatchID/ItemID/OperationID/AttemptID/ModelCallID/AssetVersionID/ReleaseID/UserID。监控到期清理积压、引用保护原因、下载完成登记失败、未知调用、重复派发意图、备份延迟、就绪失败和路由desired/observed不一致；管理页面呈现能用于发布决定的结果。
